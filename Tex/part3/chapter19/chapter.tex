\section*{Chapter at a glance}
\phantomsection
\addcontentsline{toc}{section}{Chapter at a glance}

Parts I and II have given us two complementary ways to understand language-agent systems. CoALA provides an architectural vocabulary for information storage, action space, and the decision procedure. Fan and Lan examine the mechanisms that make particular control relationships operational. We now move from those explanations to one Java teaching application. This chapter establishes the problem and the modeled world before we inspect the agent's cognitive services. We will identify the supply-chain facts represented by the application, the constraints that protect those facts, the deterministic simulator used to model the external environment, and the software modules that connect the domain to the agent runtime.

The application is a reference demonstration and teaching system. It models selected supply-chain operations; it does not connect to real suppliers, warehouses, carriers, or enterprise resource-planning systems. The code uses typed domain objects, explicit state transitions, action boundaries, persistence adapters, and testable recovery paths. One persistence boundary is important from the outset: PostgreSQL stores selected memory and runtime records and graph checkpoints, but the current repository does not provide a PostgreSQL adapter for the simulated supply-chain snapshot itself. These engineering properties make the implementation useful for learning; they do not turn it into a deployed product or establish independent experimental effectiveness.

\begin{learningbox}
By the end of this chapter, you should be able to explain the supply-chain problem being modeled; identify the main domain records and the invariants that connect them; distinguish a planning-side simulated rollout from a transition applied to the current modeled environment; distinguish a proposed action, a validated simulation command, and an observation; explain the roles of the domain, simulator, action, runtime, infrastructure, and evaluation modules; and describe what the demonstration does not claim to model.
\end{learningbox}

\section{What are we building?}
\label{sec:ch19-what-we-build}

Imagine a company that must fulfill customer orders using inventory, qualified suppliers, purchase orders, carriers, routes, and shipments. A disruption can alter one of those facts. A supplier may reduce its available capacity. A lot may be placed on quality hold. A shipment may be delayed or become eligible for rerouting. A customer order may change. The company needs to understand which commitments are affected and which recovery actions remain feasible.

The problem is not simply to produce a plausible explanation of a disruption. A useful system must distinguish at least five questions:

\begin{enumerate}
  \item \textbf{What is known?} Which orders, inventory lots, supplier capabilities, purchase orders, routes, and shipments are present in the modeled world?
  \item \textbf{What changed?} Which disruption or observation altered the facts on which the current plan depends?
  \item \textbf{What remains feasible?} Does a proposed reservation exceed available stock? Is a supplier qualified for the product? Can a route meet the revised arrival time?
  \item \textbf{What may be done?} Is the proposed operation read-only or state-changing, and has the required capability and approval been established?
  \item \textbf{What happened?} Did the simulated world accept the command, what new state was produced, and what evidence should the agent use in its next decision cycle?
\end{enumerate}

These questions belong to different parts of the application. A language model can help interpret a request or assess evidence, but it is not the authoritative source for inventory quantity, supplier capacity, order status, or approval. The domain model represents the business facts; the simulator evaluates typed transitions; the world adapter exposes the current simulated environment; the action subsystem mediates the agent's interaction with that environment; and the runtime coordinates the decision process. The later chapters will show how the application realizes CoALA's architectural roles and implements selected engineering counterparts for the control problems described by Fan and Lan's five residual bundles. These counterparts should not be read as claims of complete migration or faithful reproduction of every source mechanism.

A continuity note will prevent a misleading expectation. Product X, used in Parts I and II to illustrate a payment-service incident, remains a book-created teaching example; it is not the application implemented here. Part III deliberately moves to a different, code-backed supply-chain domain so that the reader can follow connected inventory, procurement, logistics, approval, and recovery state in one modeled environment. Chapter 18 ended Part II with a Product X composition trace and Java-like contracts. That chapter explicitly presented those contracts as engineering proposals, not as source files from this repository. Part III now examines the actual implementation. A class or interface may serve a comparable responsibility without matching the earlier illustrative name or design exactly; the later chapters will identify the correspondence and any remaining differences rather than treating the sketches as an implementation specification.

\subsection{A deliberately bounded example}

\BookExampleLabel{} The simulator test fixture provides a small, concrete world. It contains a product called Precision valve, a supplier with a product-specific capacity, an inventory location and two lots, a customer order, an open confirmed purchase order, a carrier, two routes, a shipment, an approved product substitution, and a recovery objective with a proposed candidate. The fixture is not a claim about a real company. It exists so that the rules of the model can be exercised in repeatable tests.

The fixture is intentionally small, but its records are connected: the same product appears in an order line, inventory lot, supplier capability, purchase order, and shipment. The approved substitution provides an alternative product relationship, while the recovery objective and candidate connect the business state to a possible response. We will use these links to explain why constraints must be checked across records rather than one object at a time.

The fixture does not establish that a complete supply-chain optimization problem has been solved. It gives the chapters a shared set of related records from which to explain domain constraints, simulation, and recovery. A focused capacity-reduction test will be examined in the simulator section below. The complete request-to-approval-to-execution journey is reserved for Chapter 24.

\section{The business domain: model facts before planning}
\label{sec:ch19-domain-model}

A \gls{domainmodel} is the set of concepts and relationships that an application treats as meaningful facts about its subject area. The model in this repository is intentionally selective. It is not a universal supply-chain ontology and it does not attempt to represent every commercial, regulatory, geographic, or operational detail that a real enterprise may need. It represents enough of the selected domain to exercise disruption assessment, recovery planning, state-changing actions, and feedback.

The Java source groups the domain by business concept rather than placing every class in one package:

\begin{description}
  \item[Catalog.] \texttt{Product} identifies a stockable or purchasable product. \texttt{ProductSubstitution} records a time-bounded approval to use one product in place of another, including the required quantity ratio and status.
  \item[Supplier.] \texttt{Supplier} holds supplier identity, status, version, and product-specific capabilities. A \texttt{SupplierProductCapability} includes a product, capacity, lead time, and a quality-qualification flag.
  \item[Orders.] \texttt{CustomerOrder} groups order lines, priority, status, and due time. Each \texttt{OrderLine} identifies the required product and the requested and fulfilled quantities.
  \item[Inventory.] \texttt{InventoryLocation}, \texttt{InventoryLot}, and \texttt{InventoryReservation} represent where stock is held, the state of a lot, and quantities committed to fulfill an order.
  \item[Procurement.] \texttt{PurchaseOrder} and \texttt{PurchaseOrderLine} record a supplier commitment, its status, quantities, and modeled unit cost.
  \item[Logistics.] \texttt{Carrier}, \texttt{Route}, \texttt{Shipment}, and \texttt{ShipmentLine} model transport capabilities, expected transit time, shipment status, and the order demand served by each shipment line.
  \item[Disruption and recovery.] \texttt{Disruption} records a modeled event. \texttt{RecoveryObjective} identifies the affected orders, target fulfillment time, hard constraints, status, and version. \texttt{RecoveryCandidate} is a proposed sequence of typed recovery actions associated with an objective.
\end{description}

The main domain records are connected through identifiers rather than by embedding an entire object graph into each record. A shipment line points to an order and an order line. An inventory reservation points to a lot and an order line. A purchase order points to a supplier, while its lines identify products. These relationships are checked when the world snapshot is built. That is important because a locally valid record can still be inconsistent with the rest of the modeled world.

\subsection{Quantities and money are typed values}

A domain model should prevent avoidable mistakes before those mistakes reach planning. For example, the number \texttt{10} is not enough to describe a stock quantity. Ten each, ten kilograms, and ten litres are not interchangeable. The application represents a quantity as a value and a unit of measure.

\begin{lstlisting}[language=Java,caption={Quantity arithmetic rejects operations across different units. Source: supply-chain-agent-domain/.../common/Quantity.java},label={lst:ch19-quantity}]
public Quantity plus(Quantity other) {
    requireSameUnit(other);
    return new Quantity(value.add(other.value), unit);
}

private void requireSameUnit(Quantity other) {
    Objects.requireNonNull(other, "other");
    if (unit != other.unit) {
        throw new IllegalArgumentException(
            "Unit mismatch: " + unit + " versus " + other.unit);
    }
}
\end{lstlisting}

The \texttt{Quantity} record also rejects negative values, normalizes decimal scale, and prevents subtraction from producing a negative result. A \texttt{Money} value similarly couples a non-negative decimal amount to a Java currency. Addition and comparison require the same currency. The model does not silently convert units or exchange currencies; a conversion would need its own explicit rule and source of authority.

This is a small but consequential design choice. If a planner proposes reserving 12 units, the application must know what those units measure and whether they can be compared with the lot quantity and order demand. Using typed values moves some invalid states out of the planner's prompt and into code that can be tested directly.

\subsection{An immutable, versioned view of the world}

The central world-state object for the modeled environment is \texttt{SupplyChainSnapshot}. It contains maps of the current products, substitutions, suppliers, locations, inventory lots, customer orders, purchase orders, carriers, routes, shipments, reservations, disruptions, recovery objectives, and recovery candidates. It has a version and a capture time. Each successful simulator transition creates a snapshot whose version is exactly one greater than the input snapshot. The constructor copies the builder's maps and validates references and balances before the snapshot can be created.

The word \emph{snapshot} matters. This object is an immutable view of the modeled world at a particular version. It is not itself a database, an event log, or an authorization token. The persistence layer stores records through separate interfaces. The snapshot gives the simulator a coherent input state and gives downstream components a version that can be checked when an operation is applied.

A snapshot also provides derived queries instead of asking every caller to reconstruct the same calculation. For example, it can calculate active physical reservations for a lot, the remaining available quantity at a given time, the quantity already committed to non-terminal shipments for an order line, and open supplier commitments for a product. These derived values are central to feasibility checks.

\section{Business invariants: what the model refuses to accept}
\label{sec:ch19-invariants}

A \gls{domaininvariant} is a rule that must remain true for every state accepted by the domain model. Invariants are not preferences for a planner to balance against a score. They define which modeled states are valid. The repository enforces these rules at record construction, snapshot construction, and command application, depending on the rule.

Several examples show how different records must agree:

\begin{enumerate}
  \item \textbf{Product and quantity units must agree.} A supplier capability's capacity, an inventory lot's on-hand quantity, and an order line's requested quantity must use the product's declared unit. A quantity comparison across units is rejected rather than guessed.
  \item \textbf{Available stock is not the same as stock on hand.} A lot contributes no available stock when it is not in the available quality state or when it has expired. Active reservations are subtracted from its physical quantity. The same lot therefore cannot be allocated repeatedly just because its original on-hand value remains unchanged.
  \item \textbf{An order line cannot be overcommitted.} Fulfilled quantity, active reservation quantity, and demand consumed by non-terminal shipments are checked together. A state in which those commitments exceed the requested quantity is rejected. A fulfilled order must also have its lines fully fulfilled.
  \item \textbf{A substitute must be valid for the relevant time.} A substitution must refer to two different products, have a positive ratio, and be approved during the applicable time window. The snapshot rejects overlapping approved rules for the same product pair in the model's current rule set.
  \item \textbf{A new purchase order must fit the modeled supplier capability.} A new purchase order can only be placed for an active supplier with the required product and quality qualifications. Its expected delivery cannot precede the supplier's lead time, and existing open commitments plus the new amount cannot exceed the capability's capacity. This rule governs a new placement; it does not erase a commitment that was already confirmed before a later disruption reduces supplier capacity. In that case, the existing commitment remains in the snapshot and can be flagged as at risk, as the worked example below demonstrates.
  \item \textbf{A shipment must fit its route and carrier.} Shipment references must resolve to existing route and carrier records, the carrier must support the route, and the shipment lines must reference valid order lines and products. Rerouting has further state and timing restrictions.
\end{enumerate}

These rules are not all implemented in one class. The value objects reject invalid local values; entity methods constrain valid local transitions; and \texttt{SupplyChainSnapshot} verifies relationships that require multiple records. The simulator then enforces command-specific rules, such as only placing a draft purchase order or rerouting a shipment in an allowed status.

\begin{notebox}
A business constraint, a planning objective, and an authorization rule are different things. A hard domain constraint determines whether a modeled state transition is feasible. A planner may rank several feasible recovery candidates by cost, lateness, or another represented value. An authorization policy determines whether a particular action is permitted for the current actor and context. A high planner score cannot override an invalid quantity, and a valid quantity does not itself grant permission to execute.
\end{notebox}

The model deliberately keeps these categories separate. The domain package does not decide which candidate should be preferred. The planner does not get to redefine the meaning of supplier capacity. The action authority does not make an infeasible order reservation valid. This separation is essential to the later code walkthroughs.

\section{The simulator: a deterministic model of the external world}
\label{sec:ch19-simulator}

For this teaching system, the external \gls{environment} is represented by a simulated supply-chain world. The simulator makes it possible to inspect what happens when a command changes supplier capacity, places a purchase order, applies a quality hold, delays or reroutes a shipment, reserves or releases inventory, changes demand, or records a disruption. The modeled effects can be repeated in tests without contacting an external business system.

The simulator is implemented in the \path{supply-chain-agent-simulator} Maven module. Its central class is \texttt{SupplyChainSimulator}. It receives a snapshot and a typed \texttt{SimulationCommand}, applies the corresponding rule, and returns a \texttt{SimulationResult}. The command is an input to a transition calculation. It is not itself evidence that the current simulated environment has changed.

Part I uses simulation in two related discussions that should not be collapsed into one. Chapter~6 notes that a structured simulator can generate plausible rollouts in a well-defined domain; Chapter~8 explains how planning sub-stages can interleave or iterate while an agent internally simulates candidate consequences, identifies defects, and improves proposals before taking an external action. These are related uses of simulation, but they are not one prescribed algorithm.\CoALACite{\S 4.6, planning-stage paragraph, p. 12; ``Proposal,'' p. 13} The repository provides a deterministic, domain-grounded planning rollout through \texttt{SimulatorBackedPlanningWorldModel}: it applies a candidate's typed command to an isolated \texttt{PlanningState} branch by calling the pure simulator and returns an applied or rejected world transition. This branch is not the current simulated environment. It is a structured planning calculation, not an observation from the environment and not proof that a real or current-world action has occurred. In this chapter, \emph{planning-side rollout} is a descriptive label for that implementation; it is not a new CoALA mechanism and should not be treated as identical to every form of internal reasoning simulation discussed in Chapter~8. A grounding action follows a different path: it is dispatched against the current world, checked against the expected snapshot version, and applied through the \texttt{SupplyChainSimulationWorld} port. We will use \emph{simulated-world transition} for a command committed to the current modeled environment.

\subsection{Typed commands make the requested transition explicit}

\texttt{SimulationCommand} is a sealed interface. Its permitted records define the supported transition vocabulary. A command carries a command identifier and an occurrence time, plus the identifiers and values needed for that particular transition. For example, a reservation command identifies the reservation, customer order, order line, inventory lot, fulfillment quantity, and time.

\begin{lstlisting}[language=Java,caption={A reservation command carries typed identifiers and a positive fulfillment quantity. Source: supply-chain-agent-simulator/.../command/SimulationCommand.java},label={lst:ch19-command}]
record ReserveInventory(
        String commandId,
        ReservationId reservationId,
        CustomerOrderId orderId,
        OrderLineId orderLineId,
        InventoryLotId lotId,
        Quantity fulfillmentQuantity,
        Instant occurredAt) implements SimulationCommand {
    public ReserveInventory {
        requireId(commandId);
        Objects.requireNonNull(reservationId);
        Objects.requireNonNull(orderId);
        Objects.requireNonNull(orderLineId);
        Objects.requireNonNull(lotId);
        Objects.requireNonNull(fulfillmentQuantity);
        Objects.requireNonNull(occurredAt);
        if (!fulfillmentQuantity.isPositive()) {
            throw new IllegalArgumentException(
                "fulfillmentQuantity must be positive");
        }
    }
}
\end{lstlisting}

The command constructor can check that the request is structurally meaningful. It cannot by itself determine whether the lot has enough available quantity or whether the order line can accept more commitment. Those facts require the current snapshot and are checked by the simulator and snapshot invariants.

\subsection{A pure transition produces a new snapshot and effects}

The simulator dispatches on the command type, calls the corresponding transition method, and returns a result containing the command identifier, previous version, new version, new snapshot, and a list of typed effects. It performs no database write, network request, supplier notification, carrier booking, or physical warehouse operation.

A successful transition creates a new snapshot. The helper that advances the world copies the current snapshot into a builder, increments its version exactly once, advances the capture time when the command time is later, applies the mutation, and validates the resulting snapshot. The original snapshot remains unchanged. This immutability makes it possible to compare the before and after states and prevents a caller from accidentally editing the current world outside the simulator's transition rules.

A \texttt{SimulationEffect} describes the modeled consequence. It has a type, description, affected entity references, and attributes. For example, reducing supplier capacity can produce both a capacity-change effect and an effect identifying open purchase orders that are now at risk. An effect is an auditable description of the simulated transition; its existence does not mean a real external side effect occurred.

\subsection{Worked example: reducing supplier capacity}

Return to the small test fixture. The supplier has a capability for the Precision valve product with a capacity of 100 EACH. An open confirmed purchase order already commits 30 EACH. The test applies a \texttt{ReduceSupplierCapacity} command with a new capacity of 20 EACH.

The simulator first resolves the supplier and the product capability. It requires the new capacity to use the same unit and to be strictly lower than the current capacity. It creates a supplier record with an updated capability and version. It then computes the open supplier commitment from purchase orders whose statuses consume capacity. Since the existing 30-EACH commitment exceeds the reduced 20-EACH capacity, the simulator adds an \texttt{OPEN\_PURCHASE\_ORDERS\_AT\_RISK} effect. The confirmed purchase order remains represented; the capacity reduction does not rewrite or silently cancel it.

The test method \texttt{supplierCapacityReductionFlagsExistingOpenCommitmentsAtRisk} asserts that the returned snapshot has version 1, the supplier capability is now 20 EACH, the supplier record's version has advanced, and the risk effect is present. The implementation creates the next state through a builder copied from the input snapshot, and \texttt{SupplyChainSnapshot} copies its maps on construction. The worked example therefore illustrates the immutable-snapshot design, but its test's final version-zero assertion obtains a new fixture rather than comparing the exact input object. A separate reservation test performs that direct before-and-after comparison, as noted in the test-evidence section. A companion test, \texttt{capacityCommandRejectsAnIncrease}, rejects an attempted capacity increase through the reduction operation as an invalid transition.

The example illustrates four separate facts: the command says what change is requested; the simulator checks whether that change is valid; the new snapshot records the modeled business state; and the effect explains which related commitment needs attention. The simulator does not choose a recovery plan, authorize a purchase, or notify the supplier. Those responsibilities belong elsewhere.

\section{From the simulator to agent-facing actions}
\label{sec:ch19-action-boundary}

The simulator is a domain transition engine. The agent should not call its internal methods directly or receive permission merely because a model generated a command-shaped object. The action module provides a boundary between the cognitive application and the simulated environment.

The interface \texttt{SupplyChainSimulationWorld} exposes two operations: read the current snapshot and apply a typed simulation command against an expected version. The implementation \texttt{InMemorySupplyChainSimulationWorld} is intentionally described in its source as an in-memory adapter for tests and local scenarios, not as a transactional production repository.

\begin{lstlisting}[language=Java,caption={The in-memory adapter checks the expected version and commits with compare-and-set. Source: supply-chain-agent-actions/.../grounding/InMemorySupplyChainSimulationWorld.java},label={lst:ch19-world-adapter}]
SupplyChainSnapshot before = current.get();
if (before.version() != expectedVersion) {
    throw new DomainViolation(DomainViolation.Code.CONFLICT,
        "World snapshot version is " + before.version()
            + ", expected " + expectedVersion);
}
SimulationResult result = simulator.simulate(before, command);
if (!current.compareAndSet(before, result.snapshot())) {
    throw new DomainViolation(DomainViolation.Code.CONFLICT,
        "World snapshot changed concurrently; reload and reconsider");
}
return result;
\end{lstlisting}

This is a small example of optimistic concurrency control. A caller acts on a particular snapshot version. If the version has already changed, the adapter rejects the stale request. If another thread changes the reference between the read and the compare-and-set, the second check also rejects the transition. The caller must reload the state and reconsider rather than silently applying an action to facts that are no longer current.

The compare-and-set operation is not a distributed database transaction and does not make the in-memory adapter suitable for multiple application processes. It provides a clear local concurrency boundary for the deterministic simulation. The PostgreSQL infrastructure and durable application composition are introduced later; they should not be conflated with this local adapter.

\subsection{Grounding actions and perception actions}

The action module separates state-changing \gls{groundingprocedure}s from read-only perception. \texttt{SupplyChainGroundingActions} contains typed handlers for operations such as reserving inventory, releasing a reservation, placing a purchase order, and rerouting a shipment. Each handler describes the action and its effect, declares the required capability, identifies affected resources, exposes a request fingerprint, checks its action-specific precondition, and translates an accepted request into a simulator command. The \texttt{ActionDispatcher} performs the shared dispatch checks: registered input/output types, principal authorization for the required capability and resource scope, and idempotency handling when the action descriptor requires it. For an idempotent action, it first inspects the ledger for a prior result; it then evaluates the handler precondition and acquires an execution claim only if that precondition passes. This ordering allows a completed duplicate to be acknowledged even if its original execution has made the former precondition stale. Execution follows only after the checks and claim succeed.

The reserve-inventory handler makes this boundary concrete. Its descriptor declares a domain-write effect and the \texttt{INVENTORY\_RESERVE} capability; its resource extractor identifies the affected customer order and inventory lot. The handler's precondition compares the current snapshot version with the version carried by the request. If the precondition passes and the dispatcher acquires the required idempotency claim, execution constructs a \texttt{SimulationCommand.ReserveInventory} using the operation identifier and action context. Workflow-level human approval, where required, is a separate application gate: approval does not replace capability authorization, and a capability grant does not by itself establish that the required approval has been obtained. Chapter 24 will follow how these gates are composed in the full application.

Read-only handlers are different. \texttt{SupplyChainPerceptionActions} exposes operations for reading a supplier, inventory lot, customer order, shipment, available inventory, and quality disposition. Its class comment states that these handlers expose observations rather than mutable domain objects. The \texttt{Observation<T>} record carries the value, entity reference, evidence reference, provenance, and source snapshot version. The snapshot perception adapter marks the source as the simulator and derives the provenance identifier from the snapshot version and entity reference.

This distinction is more important than it may first appear. Reading available inventory is a perception operation. Reserving inventory changes the modeled world. Both kinds of registered action pass through dispatch and its type and capability/resource checks; state-changing actions additionally require the idempotency behavior declared by their descriptors. The grounding handler checks the expected world version before it asks the world port to apply a command. The first path can provide evidence for planning; the second must satisfy domain feasibility, workflow approval where required, and action authority. A sentence in the model response saying that inventory has been reserved is neither an observation nor an executed action. This section establishes the boundary with the simulated environment; Chapter 20 will place perception and grounding alongside CoALA's full set of internal and external actions.

\section{Frameworks and infrastructure: implementation tools, not new theories}
\label{sec:ch19-framework-boundaries}

The supplied code is framework-aware. It uses LangGraph4j, LangChain4j, and PostgreSQL. This is an implementation fact, not a third theoretical foundation. CoALA and Fan and Lan remain the only overarching theories of the book.

\textbf{LangGraph4j} is used by \texttt{CognitiveCycleGraph} for application-level sequencing, conditional routing, interruptions, and checkpointing. The services and planning algorithms remain separate Java components invoked through the graph's operations. This is why the framework should not be described as implementing CoT, ToT-inspired search, or MCTS. Those strategies are Java planning components; the graph coordinates when the application invokes them.

\textbf{LangChain4j} is used at the model boundary. The repository provides adapters such as \texttt{LangChain4jRequestInterpreter} and \texttt{LangChain4jReasoningProvider} for application-owned ports. The model-facing interfaces classify a request or return a structured assessment. The reasoning service is explicitly documented as having no tools or operational authority. LangChain4j is therefore not the outer workflow engine and a model response does not itself authorize or execute a business action.

\textbf{PostgreSQL} supplies durable adapters for selected CoALA memory records, planner sessions and artifacts, intention and approval state, action-execution records, observations, resource budgets, and mechanism-specific runtime records. The separate LangGraph4j PostgreSQL saver stores graph checkpoints. These are related persistence concerns, but they are not the same state. A graph checkpoint is not automatically episodic memory, and a memory record is not automatically the entire resumable execution state. There is another boundary in the supplied code: \texttt{DurableCognitiveApplicationHost.Ports} receives a \texttt{SupplyChainSimulationWorld} adapter from its caller. The repository's only main-source implementation is \texttt{InMemorySupplyChainSimulationWorld}, which is explicitly intended for tests and local scenarios. The PostgreSQL module does not provide an adapter that persists \texttt{SupplyChainSnapshot}. Therefore, PostgreSQL durability for memory/runtime records and graph checkpoints must not be mistaken for PostgreSQL durability of the simulated supplier, inventory, order, and shipment state. Chapters 20 and 24 will show the separate contracts in context.

\begin{tipbox}
Read each framework call in the context of the Java port it serves. Ask which application-owned contract is being implemented and which authority remains outside the model or graph. This is more useful than memorizing framework annotations before understanding the responsibility they connect.
\end{tipbox}

\section{How the supplied application is composed and exercised}
\label{sec:ch19-application-composition}

The module map shows where responsibilities live; two application classes show how the cognitive runtime is assembled. \texttt{CognitiveCycleApplicationGraph} exposes the \texttt{compileFull} composition method, which connects the decision and lifecycle services with \texttt{CognitiveCycleGraph}. \texttt{DurableCognitiveApplicationHost} supplies the durable host: it constructs the PostgreSQL-backed memory and runtime stores and the graph checkpoint saver, while receiving application-specific ports and adapters through its \texttt{Ports} record. Those injected ports include the request interpreter, reasoning provider factory, perception port, planning world model, and \texttt{SupplyChainSimulationWorld}. This keeps the cognitive runtime's persistence separate from the adapter that owns the current simulated business snapshot.

A reader looking for a runnable application should notice one limitation. The only \texttt{main} method in the supplied \texttt{supply-chain-agent-app} module is \texttt{Phase0Application}. It is a local intake smoke program: it compiles \texttt{SupplyChainIntakeGraph}, supplies a fixed chat-model response of \texttt{READY}, uses the in-memory \texttt{MemorySaver}, and prints the intake result. It does not launch the complete cognitive-cycle graph or the durable host. The repository therefore provides a full application composition API and test-backed execution paths, but it does not provide a finished user-facing interface or a single command-line entry point for the complete agent. We should not invent one in the book.

The repository contains several persistence and restart tests, but they do not all test the same boundary. Treat them as separate pieces of evidence rather than as one claim that the complete application can restart after every kind of interruption:

\begin{enumerate}
  \item \textbf{Durable-host reconstruction at a clarification boundary.} The app-module test \texttt{DurableCognitiveApplicationHostPostgresIntegrationTest} opens the actual durable host, writes a working-memory marker, starts a cycle that pauses for clarification, closes the host, and opens a new host instance against the same PostgreSQL database. The replacement host reads the memory marker and resumes the same graph checkpoint. The test's planner strategies deliberately fail if invoked, so this path stops before planning and external effects. It demonstrates same-JVM host-instance replacement, memory persistence, and checkpoint resume at this boundary; it is not a process-restart or business-effect test.
  \item \textbf{Two-cycle simulated business flow with host reconstruction.} The evaluation-module test \texttt{DurableCognitiveApplicationHostEndToEndPostgresIntegrationTest} uses deterministic test interpretation and reasoning adapters. It binds approval to the selected action, applies a simulated effect, loses the acknowledgement, reconstructs the host, reconciles without redispatch, then starts a second cycle that consumes the first cycle's observation. The simulator-world and approval-authority adapters remain alive across host reconstruction. Some artifact codecs in this test also use same-process registries behind PostgreSQL tokens. This is the strongest end-to-end business-flow demonstration in the repository, but it does not prove fresh-JVM serialization of the complete business environment.
  \item \textbf{Replacement-pool reconciliation in a focused workflow.} \texttt{M8B4C}\allowbreak\texttt{Restart}\allowbreak\texttt{Reconciliation}\allowbreak\texttt{IntegrationTest} closes the original Hikari pool, creates a replacement pool, rebuilds its repositories and a small test workflow graph, reloads approval, intention, B6 budget, checkpoint, and action-ledger state from PostgreSQL, and reconciles an ambiguous provider write. The provider simulator is retained by the test outside those host objects. This is a same-JVM pool/repository replacement test, not the complete cognitive application graph or a child-process restart.
  \item \textbf{Focused write/reconcile across independent JVMs.} \texttt{M8B4}\allowbreak\texttt{ForkedJvm}\allowbreak\texttt{ProcessRestart}\allowbreak\texttt{IntegrationTest} launches two child JVMs. The first persists approval and intention state, dispatches a focused test action, records a provider effect in a marker file, and checkpoints an unknown outcome. The second starts with fresh process-local objects, restores PostgreSQL state, reconciles the operation, and verifies that it is not dispatched twice. This is genuine process-boundary evidence for a deliberately small workflow and deterministic provider probe; it is not a restart of the full supply-chain application or its simulated-world snapshot.
  \item \textbf{Full cognitive-cycle graph checkpoint across JVMs.} \texttt{M8B4FullGraphWorkflowTest} launches child JVMs around the full cognitive-cycle graph assembled by the evaluation host. It pauses at a clarification boundary, halts the first process, then restores the PostgreSQL graph checkpoint in the second process and continues. The scenario uses test-owned in-memory supply-chain world/effect adapters and has not yet crossed the clarification/authorization boundary when it pauses. This demonstrates fresh-JVM checkpoint recovery for the full graph harness, not recovery after a committed simulated-world transition and not restart of \texttt{DurableCognitiveApplicationHost} itself.
\end{enumerate}

Taken together, these tests cover durable host reconstruction, two-cycle simulated business flow, repository/pool replacement, a focused write/reconcile process boundary, and full-graph checkpoint resume at clarification. They must not be compressed into the stronger claim that PostgreSQL persists the simulated supply-chain world across a fresh-JVM restart: the supplied \texttt{SupplyChainSimulationWorld} implementation remains in-memory, and the end-to-end business-flow test keeps that adapter alive while rebuilding the host. Chapter 24 will compare the paths in more detail when the complete workflow is traced.

\section{What the tests demonstrate}
\label{sec:ch19-test-evidence}

The persistence and restart tests above exercise different runtime boundaries. The examples in this section return to the domain and simulator tests, because they show which business facts are protected before an agent proposes or dispatches an action. This layered evidence is useful because a final successful workflow alone may not reveal which layer enforced a rule.

For this chapter, three test groups are particularly instructive:

\begin{description}
  \item[\texttt{QuantityTest}.] It checks arithmetic with matching units, rejects unit mismatch and underflow, and rejects negative quantities.
  \item[\texttt{SupplyChainSnapshotInvariantTest}.] It checks over-reserved physical stock, in-flight shipment quantity against order demand, the relationship between delivered shipment quantity and recorded fulfillment, overlapping approved substitution windows, and duplicate product SKUs.
  \item[\texttt{SupplyChainSimulatorTest}.] It exercises purchase-order qualification, lead time and capacity; reservation availability and substitution ratios; quality holds; shipment delay and rerouting; demand changes; disruption recording; and determinism for the same snapshot and command. Its \texttt{exactProductReservationReducesAvailableInventoryAndIsImmutable} test also compares the same input snapshot before and after a reservation transition, directly checking that this transition does not mutate the input view.
\end{description}

These tests establish that particular rules are encoded and that particular inputs produce asserted outcomes. They do not prove that the model captures every relevant supply-chain constraint, that recovery plans are optimal in a real business, or that adding a cognitive mechanism improves task success. Those are different claims requiring different evidence. The independent experimental phase is deliberately kept separate from the teaching application's implementation and CI acceptance. The five persistence/restart paths described in Section~\ref{sec:ch19-application-composition} support different recovery claims; none demonstrates that PostgreSQL persists the simulated business snapshot across a fresh-JVM restart. Test claims should remain tied to the specific command path and assertion that provide the evidence.

This chapter has established the domain, the simulated environment, and the high-level repository boundaries. The next chapters follow the same progression from responsibility to implementation:

  \item \textbf{Chapter 20 -- CoALA in code.} We will map the Part I architecture onto the actual memory services, internal and external action contracts, and planning interfaces. The discussion will preserve the difference between the CoALA framework and the engineering choices used by this application.
  \item \textbf{Chapter 21 -- B1 and B3.} We will follow evidence from memory candidates through B1 selection and into B3's bounded workspace admission and broadcast. The chapter will show why retrieval and workspace admission are different decisions.
  \item \textbf{Chapter 22 -- B2.} We will trace a typed impasse through bounded recovery, parent-state protection, validation of the returned result, and the separate lifecycle for promoting reusable recovery knowledge.
  \item \textbf{Chapter 23 -- B4 and B6.} We will examine persistent intention and method authority alongside uncertainty, resource limits, interruption, and stopping. Their complementary authority boundaries will remain explicit.
  \item \textbf{Chapter 24 -- application composition.} We will assemble the services into the LangGraph4j runtime, explain LangChain4j and PostgreSQL boundaries, and walk through the test-backed simulated workflow without conflating separate test scenarios.
\end{enumerate}

The purpose is not to reproduce the whole repository in prose. Each chapter will select the code that reveals an important contract or transition, explain how the selected component connects to its neighbors, and point to the actual module and tests. The reader should be able to move from a concept in Parts I or II to the class that realizes the corresponding responsibility, then follow the execution path far enough to understand what the code does and does not guarantee.

\begin{chapterrecap}
The supply-chain application is a reference teaching demonstration, not a deployed enterprise integration. Its modeled operational environment uses a deterministic simulator; model-backed cognitive decisions are not thereby guaranteed to be deterministic. Its domain module represents selected products, suppliers, orders, inventory, procurement, logistics, disruptions, and recovery records. Typed quantities and snapshot validation protect relationships across those records. The simulator applies typed commands to an immutable, versioned snapshot and returns typed effects; it does not contact real-world systems. Planning can use the same pure transition logic to explore an isolated candidate branch, while a grounding action uses the world adapter to advance the current simulated environment. Agent-facing perception actions return provenance-bearing observations. PostgreSQL persists selected memory/runtime records and graph checkpoints, but the supplied repository does not include a PostgreSQL-backed adapter for the simulated supply-chain snapshot. Eleven Maven modules separate business facts, simulation, cognitive capabilities, mechanisms, planning, runtime, persistence, application composition, and evaluation. LangGraph4j, LangChain4j, and PostgreSQL are implementation technologies, not additional theoretical foundations.
\end{chapterrecap}

\begin{enumerate}
  \item Why is a generated explanation of a supplier disruption not enough to establish the current supplier capacity or open purchase-order commitment?
  \item Which domain records are needed to determine whether a customer order line can accept another inventory reservation?
  \item What does \texttt{Quantity} prevent that would be easy to overlook if all quantities were represented as untyped decimal numbers?
  \item Why does \texttt{SupplyChainSnapshot} validate relationships across more than one record?
  \item What is the difference between a \texttt{SimulationCommand}, a \texttt{SimulationResult}, and a \texttt{SimulationEffect}?
  \item Why does the simulator return a new snapshot rather than mutating the existing snapshot?
  \item What does the expected-version check protect against, and what does the in-memory compare-and-set not guarantee?
  \item How do perception actions differ from grounding actions?
  \item Why should the module dependency diagram not be interpreted as a deployment diagram?
  \item What responsibilities belong to LangGraph4j and LangChain4j in this repository, and what responsibilities remain in ordinary Java components?
  \item How does a planning-side simulator rollout differ from the internal reasoning simulation discussed in Chapter~8, and from applying a grounding action to the current simulated world?
  \item Which records and checkpoints are persisted in PostgreSQL, and which simulated-world state is supplied through an injected adapter?
  \item Why are host-instance reconstruction and fresh-JVM checkpoint resume different test claims?
  \item Which claims can the domain and simulator tests support, and which claims would require independent experiments?
\end{enumerate}
\end{reviewquestions}

\paragraph{Practical exercise.} Start with the supplier-capacity test fixture. Record the supplier's original product capacity and open purchase-order commitment. Apply the test's capacity-reduction command. Draw the before-and-after snapshot boundary and list the effects returned by the simulator. Then answer four questions: Which component decides whether the new capacity value is valid? Which component computes whether existing commitments are at risk? Which component would authorize a corresponding state-changing action if the agent initiated it? Which observation should be made available to the next decision cycle? Do not treat the test's simulated transition as a message sent to a real supplier.
