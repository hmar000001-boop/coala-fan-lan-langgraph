Chapter 19 established the modeled supply-chain domain, deterministic simulator, module responsibilities, and evidence boundaries. Chapters 20--23 then traced CoALA into the application and examined the B1, B2, B3, B4, and B6 mechanisms. This final Part III chapter composes those strands into one request-driven application: from typed service contracts and the LangGraph4j graph to the durable host, PostgreSQL boundaries, model-facing adapters, approval, simulated dispatch, and reconciliation. Its main walkthrough follows two related supply-chain cycles and distinguishes five restart paths that exercise different boundaries.

\begin{learningbox}
By the end of this chapter, you should be able to explain which component owns graph routing, mechanism decisions, domain authority, and simulated-world truth; what the durable host assembles; and which records are stored by PostgreSQL, delegated through injected ports, or retained outside the graph. \end{learningbox}

\section{From contracts and services to one application}
\label{sec:ch24-contracts-services-application}

An application graph needs more than a collection of nodes. Each node must obtain a typed result from an operation, and each operation must have a clear owner. The repository keeps these responsibilities in separate Java components rather than placing all policy in the graph class or the durable host.

\texttt{CognitiveCycleOperations} is the application-owned port used by the graph. Its methods describe the work that a cycle may request: interpret a request, load context, retrieve and accept evidence, prepare a workspace, propose and evaluate candidates, resolve an impasse, govern an intention, assess uncertainty, obtain human control or approval, revalidate a plan, execute an authorized candidate, observe and reconcile an external effect, update working memory, record an episode, or escalate. The result records in this interface make the operation boundary explicit. They do not prescribe how each service performs its work.

Two service groups provide the substantive implementation. \texttt{CognitiveCycle\allowbreak DecisionServices} composes retrieval, B1 selection, B3 workspace admission and broadcast, planner routing, candidate evaluation, and planning artifacts. \texttt{CognitiveCycle\allowbreak LifecycleServices} composes interpretation and memory lifecycle with B2 recovery, B4 intention governance, B6 meta-control, authorization, action dispatch, observation, and outcome recording. \texttt{CognitiveCycleServiceOperations} is the thin adapter that forwards the graph's operations to those two groups. The adapter is not a second policy engine.

The application-level \texttt{CognitiveCycleApplicationGraph} builds and compiles the full graph from the decision and lifecycle services. Its production overload also checks that M5 planning, M3 reasoning/action execution, and B6 share the exact same durable \texttt{ResourceBudgetExecutionGuard} instance. This is object-identity wiring: equivalent-looking but separately constructed guards are not accepted as one shared account. The graph builder still does not own the rules for supplier feasibility, capability authorization, plan approval, memory writes, or B4/B6 policy.

\section{The actual cognitive-cycle graph}
\label{sec:ch24-actual-graph}

The graph class is where the application makes its control sequence explicit. Its named nodes group into six functional regions: ingress and interpretation; context, uncertainty, and evidence; workspace and planning; B2 recovery and B4/B6 governance; authorization and execution; and observation, memory update, learning, completion, or escalation. The graph registers more nodes than any single request will visit. A read-only request may finish without approval; a write request may pause for an exact approval; missing evidence may interrupt retrieval; an impasse may branch into B2; meta-control may request evidence, downshift planning, return to proposal, wait for a human, or stop.

\section{What LangGraph4j owns---and what it does not}
\label{sec:ch24-langgraph-boundary}

The application uses LangGraph4j for graph construction and compilation, node execution order, conditional routing, human interruption, checkpoint persistence, and resume. In the source comments, the graph is described as owning sequencing/routing/interruption/checkpointing while the application services and planning algorithms remain separately callable Java components. This is the runtime boundary selected by this application, not a claim that CoALA requires LangGraph4j or that the graph library implements B1, B2, B3, B4, or B6.

\texttt{CognitiveCycleState} is the graph's checkpoint-friendly projection. It carries a compact set of IDs, versions, references, flags, and routing information. For example, the state may identify a working-memory record and its version, an evidence set, a workspace snapshot, an intention and its version, a selected candidate, an approval, an action operation, or an observation. The referenced object is not thereby copied into the graph state or made authoritative there. A checkpoint can say which intention version the cycle last saw; the B4 repository remains authoritative for the current intention. A checkpoint can retain an observation ID; the observation repository and simulator evidence still determine the observation's content and status.

\BookDiagram[0.55\textheight]
  {Tex/diagrams/generated/part3/chapter24/graph-state-and-authoritative-records.png}
  {The graph state carries references and routing data. CoALA memory, B1/B2/B3/B4/B6 records, approvals, action ledgers, observations, and simulator state remain in their owning repositories or external adapters. A PostgreSQL checkpoint serializes the graph projection; it does not merge these authorities into one state store.}
  {fig:ch24-graph-state-versus-authorities}

This distinction matters after interruption. Resuming a graph from its checkpoint tells the runtime where the cycle paused and what identifiers were in play. It does not prove that an external simulator applied a command, that an approval is still current, that a resource reservation is unexpired, or that a working-memory write succeeded. Those facts must be reloaded or revalidated through their owners before the graph continues.

\section{The durable host and PostgreSQL composition}
\label{sec:ch24-durable-host}

\texttt{DurableCognitiveApplicationHost} is the composition root and lifecycle boundary for the full cognitive application. \texttt{open(...)} reads database settings, creates the pooled data source, applies migrations, and assembles the host. \texttt{assemble(...)} wires the repositories, services, shared resource guard, graph, and PostgreSQL checkpoint saver. The \texttt{Ports} record supplies trusted external adapters such as request interpretation, planning strategies, authority, perception, simulator access, domain decisions, codecs, and the clock. The host does not itself invent supplier feasibility or approval policy; it assembles the objects whose contracts own those decisions.

The assembly has several distinct layers. The four CoALA memory services use their memory repositories. B1 receives its feature repository and learning service. B2 receives impasse/case, child-step, draft, and artifact persistence. B3 receipts and separately verified outcomes are backed by PostgreSQL, while the current-cycle workspace repository is explicitly an \texttt{InMemoryWorkspaceRepository} and therefore ephemeral in this host composition. B4 uses the scope-bound recovery-intention repository. B6 resource reservations and usage use the PostgreSQL runtime budget ledger and shared guard. Uncertainty assessments have a different owner: the required \texttt{lifecycleDomain} port creates each immutable assessment revision and resolves the exact revision referenced by the cycle. This gives Chapter 23's phrase \emph{host-owned assessment store} a precise meaning: the store belongs behind the lifecycle-domain adapter supplied to the host, not to a repository constructed internally by \texttt{DurableCognitiveApplicationHost}. The port contract requires the injected adapter to store revisions durably, but the host does not construct a PostgreSQL repository for the base assessment records. No concrete production lifecycle-domain adapter is included in the supplied application module; the full-host integration test injects a deterministic test adapter. When an uncertainty-calibration codec is supplied, the host additionally creates a PostgreSQL repository for calibration profiles; calibrated interpretations are returned to the lifecycle-domain adapter through its persistence hook. The host then builds decision/lifecycle services, compiles the graph, and supplies the graph-schema serializer to the PostgreSQL saver factory.

\section{Approval, dispatch, and reconciliation}
\label{sec:ch24-approval-dispatch-reconcile}

A candidate selected by planning is still only a proposal. In the graph, a state-changing candidate moves to authorization, and the authorization service determines whether an exact approval is required or whether the request is denied. If approval is required, the graph pauses. The host supplies a response and authenticated actor/approver reference. The graph resolves that response against the durable approval record and the exact plan/version, then revalidates approval binding, candidate freshness, feasibility and intention authority immediately before dispatch.

The action layer adds further independent checks. \texttt{ActionDispatcher} resolves the registered handler and input/output types, checks the capability against the requested resources, requires an idempotency key for a state-changing action, inspects the operation ledger, evaluates preconditions, obtains an action claim (with a fencing token when the ledger supports fenced claims), and executes through the optional resource budget. On success it records a receipt. If the handler may already have produced an external effect but the receipt cannot be committed, the action is recorded as \texttt{UNKNOWN\_OUTCOME}. A runtime failure from a mutating handler is also treated as an unknown outcome unless the failure is definitive. The correct next step is reconciliation, not a blind retry.

\BookDiagram[0.58\textheight]
  {Tex/diagrams/generated/part3/chapter24/approval-dispatch-unknown-outcome-reconciliation.png}
  {The state-changing execution path separates proposal, plan-bound approval, pre-dispatch revalidation, capability/idempotency/fencing checks, execution, unknown transport outcome, and authoritative-world reconciliation. The simulator's evidence can resolve the business outcome without rewriting the transport ledger's recorded ambiguity.}
  {fig:ch24-approval-dispatch-reconciliation}

The dispatcher's receipt boundary is important because the handler may return after an external effect has already happened. A later failure to construct or persist the receipt cannot safely be reclassified as “nothing happened.” The code therefore records an unknown outcome and requires the owning workflow to reconcile the external effect before replay. The action ledger's result is a transport/execution record; the simulator's observation is evidence about the business-world result. Those are related but not interchangeable records. The \texttt{ActionDispatcherTest} references below establish duplicate suppression and authorization ordering; the unknown-outcome and no-redispatch claims are supported by the REQ-09 and M8B4C integration paths, not by those two unit assertions alone.

\section{The primary walkthrough: two REQ-09 cycles}
\label{sec:ch24-req09-walkthrough}

\subsection{Cycle 1: approve, apply once, lose the acknowledgement, reconcile}

The first host instance initializes the scope/execution graph and runs interpretation, context loading, retrieval, workspace/planning, B4/B6 governance, and authorization until a state-changing candidate reaches the exact plan-bound approval boundary. The test asserts that the run is interrupted, an approval ID is checkpointed, the selected candidate exists, and the simulator transition count remains zero. This is the critical negative assertion: cognition and planning did not mutate the simulator before approval.

After the first host closes, the external test authority approves the exact request. A second host instance opens the same durable scope and resumes the same thread. The test simulator is configured to apply the effect and then lose the acknowledgement. The test deliberately interrupts the host after the external effect but before reconciliation. The simulator transition count is one, its version has advanced once, and the recorded action batch is \texttt{UNKNOWN\_OUTCOME} with one item marked outcome-unknown.

A third host instance is then opened from the same PostgreSQL-backed state. It resumes at reconciliation. The simulator's authoritative snapshot shows the applied effect; the graph records an \texttt{OBJECTIVE\_SATISFIED} observation and completes the cycle without dispatching the action again. The transition count remains one. The observation is written to CoALA working memory, and the B4 intention becomes \texttt{COMPLETED} only after the simulator-backed satisfaction proof has been reconciled. The action batch remains \texttt{UNKNOWN\_OUTCOME} at the transport level: authoritative business evidence resolves the real-world question without rewriting the historical fact that the acknowledgement was lost.

The business effect in this walkthrough is a typed inventory reservation, not an unconstrained model-issued command. The REQ-09 test selects the \texttt{SupplyChainGroundingActions.ReserveInventory} action, checks that the planned simulator command is a \texttt{SimulationCommand.ReserveInventory}, and constructs a \texttt{ReserveInventoryRequest} using the current snapshot version and the exact reservation, order, order-line, lot, and fulfillment-quantity values. This is the point where the approved cognitive plan becomes a domain-specific request to the simulated world. See the \href{https://github.com/haythemabr/supply-chain-agent/blob/6329aec82e1d8b4f19b68986a0d4cf0c448f697f/supply-chain-agent-evaluation/src/test/java/dev/supplychain/agent/evaluation/DurableCognitiveApplicationHostEndToEndPostgresIntegrationTest.java\#L862-L883}{REQ-09 test's reservation construction} and the \href{https://github.com/haythemabr/supply-chain-agent/blob/6329aec82e1d8b4f19b68986a0d4cf0c448f697f/supply-chain-agent-simulator/src/main/java/dev/supplychain/agent/simulator/command/SimulationCommand.java}{typed simulator command definition}.

\section{Five restart paths, five different claims}
\label{sec:ch24-restart-boundaries}

The five representative paths introduced in Chapter 19 are intentionally different. REQ-09 reconstructs the full durable host through three host instances in one JVM while retaining the simulator and approval authority. A second test reconstructs the durable host and resumes a clarification checkpoint after a host/pool replacement, but it does not enter planning or create a business effect. M8B4C replaces pools and repositories around a smaller test workflow and reconciles an ambiguous provider write, again within one JVM. M8B4D uses two child JVMs for a focused action-ledger/provider probe. The full-graph test also uses child JVMs, but it resumes at clarification and terminates in escalation rather than reconciling a completed simulator effect. These paths should not be collapsed into a claim that “the full agent restarts after any external write.”

\section{Chapter recap}
\label{sec:ch24-recap}

\begin{chapterrecap}
The application is a composition, not a graph wrapped around a database. LangGraph4j owns the request-cycle schedule, conditional routes, interruption points, checkpointing, and resume. Application-owned Java services retain retrieval, planning, mechanism, lifecycle, domain, authorization, and execution responsibilities. LangChain4j-facing adapters translate model results into typed contracts; the primary REQ-09 workflow deliberately uses deterministic interpreter and reasoning adapters, so it is not a live-model evaluation.

The persistence boundary is similarly divided. PostgreSQL contains the configured CoALA memory, mechanism/runtime, approval/action, and graph-checkpoint records; the exact records and owners differ. The B3 workspace snapshot remains ephemeral in this host composition, and the simulated supply-chain world is authoritative through its injected adapter rather than through the graph checkpoint. Base B6 uncertainty assessments are supplied through the injected lifecycle-domain port: the contract requires durable, exact-revision storage, but the host does not build a PostgreSQL repository for them. A configured calibration profile repository is a separate, optional facility.

The REQ-09 test demonstrates two approved state-changing cycles under one memory scope. Its first cycle applies an effect once, loses the acknowledgement, reconciles from the simulator, writes the observation to memory, and completes the B4 intention. The second cycle consumes the earlier observation and performs a separately approved effect. Three host instances participate, but all are in one JVM while the test simulator and approval authority remain alive. The other four restart paths test different boundaries: durable-host clarification resume, focused same-JVM pool-replacement reconciliation, a focused two-JVM action-ledger probe, and full-graph two-JVM clarification resume. None proves that PostgreSQL persists the simulated business world across a fresh-JVM restart.
\end{chapterrecap}

\section*{Source and implementation note}
\addcontentsline{toc}{section}{Source and implementation note}

CoALA supplies the architectural vocabulary for memory, internal and external action, and the decision procedure; Fan and Lan supply the mechanism framing used in the earlier Part III chapters. Neither source prescribes this Java service decomposition, the exact graph topology, LangGraph4j checkpoint configuration, LangChain4j adapters, PostgreSQL repository selection, action-ledger protocol, simulator, or the five test workflows. Those are engineering choices in the supplied repository. The chapter distinguishes repository-backed claims from injected-port contracts: in particular, durable storage of base B6 uncertainty assessments is required by the lifecycle-domain interface but is not implemented by a host-created PostgreSQL assessment repository in this snapshot.

All application scenarios and tests use deterministic or test-owned adapters. They do not establish a live supplier, carrier, warehouse, or model-provider integration; persistence of the simulated world across process boundaries; production deployment readiness; empirical benefit from the mechanisms; or causal superiority of the proposed composition. B5/GraSP is not implemented.
