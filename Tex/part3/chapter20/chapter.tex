This chapter follows one path through the code. By the end of this chapter, you should be able to map CoALA's three architectural dimensions to the application without assuming a one-class-per-concept design; explain the distinct responsibilities of working, episodic, semantic, and procedural memory; distinguish retrieval from B1 selection and B3 workspace admission; trace the internal actions for retrieval, reasoning, and learning; distinguish perception from grounding; follow a planning request through an isolated simulator-backed planning state; compare the three planner strategies; and explain why an evaluated candidate is not permission to execute it.
\end{learningbox}

\section{From CoALA's three dimensions to the code}
\label{sec:ch20-coala-map}

Chapter 2 introduced three questions that help describe a language agent: what information it maintains, what actions it can perform, and how its decision procedure coordinates those actions. The questions remain useful when we read an implementation, but their answers do not have to occupy three separate classes or services. CoALA is an architectural framework, not a prescription for Maven modules, deployment processes, or class names.\CoALACite{Section 4, Figure 4A, and Table 2}

In this application, information storage is represented by the memory module and its repositories. Working memory holds active context within an application-defined memory scope; episodic memory retains reviewed experience; semantic memory manages facts with provenance and temporal validity; and procedural memory manages versioned procedure records. The action space is represented by typed handlers. Some handlers perform internal operations on the agent's information, some observe the simulated supply-chain environment, and others request changes to that environment. The decision procedure is represented by planning strategies, candidate evaluation, and the higher-level runtime that coordinates them.

The last point needs care. A planner is not the entire decision procedure. It proposes candidate paths under a request and budget. The application still needs to decide which strategy to invoke, evaluate what the strategy returns, and coordinate later execution. This chapter examines the memory, action, and planning contracts. Chapter 24 will show how the graph runtime sequences them. The eleven-module organization and framework boundaries were introduced in Section~\ChapterNineteenModulesRef; we will refer to those module names where useful rather than repeat the module tour.

\section{Memory in the application: four distinct responsibilities}
\label{sec:ch20-memory}

A supply-chain request may mention a current shipment, a previous recovery attempt, a supplier fact, or a reusable procedure. These are all information, but they are not the same kind of information. Treating them as one growing text history would make it difficult to state whether a record is current, verified, scoped to the present task, or approved for reuse. CoALA distinguishes working, episodic, semantic, and procedural memory because each has a different role in the agent's operation.\CoALACite{Section 4.1, pp. 9--10}

The Java implementation preserves that separation through four models and services. The following table is a reading aid, not a claim that CoALA requires four databases or four independent services.

\subsection{Working memory: active, scoped, and versioned}
\label{subsec:ch20-working-memory}

Working memory contains information that is active for a reasoning process. It is not simply the latest conversation text. In the application, \texttt{WorkingMemorySnapshot} is an immutable record for an application-defined \texttt{MemoryScopeId}. A scope may represent a tenant, business unit, or execution family; it is not necessarily identical to one graph invocation or checkpoint. It has an identifier, a version, creation and update times, an expiry time, typed values, hypotheses, and the evidence references associated with the current values and hypotheses. The values are represented through the \texttt{MemoryValue} type rather than being stored as arbitrary untyped strings.

The service changes the snapshot through version-checked operations. The following excerpt shows the central update path:

\begin{minipage}{\linewidth}
\begin{lstlisting}[language=Java,caption={Updating one working-memory slot with version and expiry checks.},label={lst:ch20-working-memory-put}]
public WorkingMemorySnapshot put(
        WorkingMemoryId id, long expectedVersion, String key,
        MemoryValue value, List<EvidenceReference> evidence,
        Instant now) {
    var current = load(id);
    requireVersion(current, expectedVersion);
    requireNotExpired(current, now);
    var replacement = current.put(
        key, value, evidence, now, now.plus(ttl));
    return repository.compareAndSet(id, expectedVersion, replacement);
}
\end{lstlisting}
\end{minipage}

The method does not mutate the existing snapshot. It first checks that the caller's expected version is current and that the snapshot has not expired. It then creates a replacement snapshot and asks the repository to compare-and-set it. If another update has already advanced the version, a stale write is rejected instead of silently overwriting newer context. The snapshot itself recomputes its evidence list from the evidence attached to its current slots and hypotheses. Removing a value therefore also removes evidence that is no longer referenced by the active snapshot.

Hypotheses are represented separately from ordinary values. Their statuses distinguish proposed, supported, refuted, and withdrawn hypotheses. A supported hypothesis must carry supporting evidence; a refuted hypothesis must carry contradiction evidence. These constraints make the status meaningful rather than allowing the model to label a guess as established without recording why.

\begin{tipbox}
Do not equate a CoALA working-memory snapshot with the runtime's graph state. \texttt{WorkingMemorySnapshot} is the application's model of active cognitive information. \texttt{CognitiveCycleState} is state used to route and execute the graph. A LangGraph4j checkpoint is a persisted representation of graph execution state. The three may contain references to related information, but they answer different questions. Chapter 24 will examine the graph-state and checkpoint boundary.
\end{tipbox}

\subsection{Episodic memory: record experience without treating it as truth}
\label{subsec:ch20-episodic-memory}

Episodic memory represents experience: events that occurred, the entities involved, the outcome, and the evidence associated with the episode. The application models an episode through an \texttt{Episode} record containing its scope, times, entities, events, evidence, provenance, status, and review metadata.

Recording is not the same operation as verification. A new episode begins in the \texttt{RECORDED} status. It has a bounded retention period while unverified. If the provenance is model-derived, the recording service requires supporting evidence. A separate review operation can verify or reject the episode. Only verified episodes are eligible for trusted experience retrieval. A verified episode may later be superseded, while its review and supersession times preserve what was known at earlier points in time.

The transition is explicit in the episode model:

\begin{minipage}{\linewidth}
\begin{lstlisting}[language=Java,caption={Verification is a separate, evidence-bearing transition.},label={lst:ch20-episode-verify}]
public Episode verify(String actor,
                      EvidenceReference reviewRef,
                      Instant at) {
    if (status != EpisodeStatus.RECORDED) {
        throw new IllegalStateException(
            "only recorded episodes can be verified");
    }
    if (at.isBefore(recordedAt)) {
        throw new IllegalArgumentException(
            "verification cannot precede recording");
    }
    return new Episode(id, scopeId, version + 1, title, summary,
        outcome, EpisodeStatus.VERIFIED, startedAt, completedAt,
        recordedAt, null, entities, events, merge(evidence, reviewRef),
        provenance, require(actor, "actor"), at, reviewRef, null);
}
\end{lstlisting}
\end{minipage}

\subsection{Semantic memory: facts have provenance and time}
\label{subsec:ch20-semantic-memory}

Semantic memory represents knowledge expressed as facts. In this application, a \texttt{SemanticFact} has a key and value, a scope, provenance, status, and two temporal dimensions. Valid time describes when the fact applies in the modeled world. Known time describes when the application had accepted that version of the fact. These dimensions allow a query to ask not only what is considered valid at a business time, but also what the system knew at a particular decision time. The semantic review action has its own capability and evidence contract, but the current fact model does not retain a proposing principal for an enforced proposer/reviewer identity comparison.

A proposed fact is not automatically active. Under the repository's conservative default admission policy, only \texttt{AUTHORITATIVE\_SYSTEM} and \texttt{HUMAN\_VERIFIED} provenance may be activated without human review. Other provenance categories—including verified documents, verified episodes, simulator observations, unverified documents, and model-derived content—require the explicit review path. Replacing an active fact is also governed: the service checks versions and matching keys, and the repository performs old-fact supersession and new-fact activation as one operation. A temporal revision can divide a timeline into contiguous replacement segments rather than silently overwriting history.

This is useful in a supply-chain setting because the statement “supplier capacity is 40 units” is incomplete without knowing which supplier/product capability it describes, when that capacity applies, where the information came from, and when the application accepted it. Semantic memory supplies those distinctions. It does not guarantee that the original source was correct; it preserves the provenance and admission decisions that the application can inspect.

\subsection{Procedural memory: governed procedure versions}
\label{subsec:ch20-procedural-memory}

Procedural memory represents how the agent may carry out a recurring task. The implementation stores a versioned \texttt{ProcedureVersion} with a kind, description, artifact reference, provenance, lifecycle status, and predecessor relationship. Its state progresses through \texttt{DRAFT}, \texttt{VALIDATED}, and \texttt{ACTIVE}; an active version may later become \texttt{RETIRED}. A draft may instead be \texttt{REJECTED}.

Validation and activation are distinct transitions. Validation records a validator and time; activation requires the validated state and records an approver and activation time. In the in-memory reference repository, activating a replacement performs the predecessor's retirement and the new version's activation inside one synchronized repository operation. There is no separately registered retirement action in the learning-action catalog. Procedure validation, rejection, and activation enforce distinct-principal checks against the author; activation also requires the approver to differ from the validator. These actor-separation checks are specific to the procedural lifecycle. Episodic and semantic review use separate capabilities and evidence, but their current models and handlers do not enforce the same author-versus-reviewer identity comparison. A reference to a procedure artifact is not, by itself, an executable skill graph.

\begin{warningbox}
Procedural memory in this repository must not be described as GraSP or as a reproduction of the B5 skill-DAG mechanism. It is an explicit, versioned memory model with governed lifecycle transitions and artifact references. It does not provide GraSP's typed skill-graph retrieval, compilation, node verification, local repair, and fallback chain. Part II established why B5 is a closed candidate in Fan and Lan's bounded review; the application does not reopen that result by naming a store “procedural memory.”
\end{warningbox}

\subsection{Cross-store retrieval is not yet B1 selection or B3 admission}
\label{subsec:ch20-memory-retrieval}

The four memory responsibilities become useful to a decision process when the application can retrieve them through one typed result. \texttt{MemoryRetrievalService} accepts a \texttt{MemoryRetrievalQuery} containing a scope, optional entity, optional semantic predicate, optional working-memory identifier, valid time, known time, and a per-type limit. The query shares a scope and request context, but the four stores do not apply identical temporal semantics. Working memory is loaded by identifier, checked for scope equality, and accepted when its expiry is after \texttt{knownAt}; the service returns the currently stored snapshot rather than reconstructing it as of a historical time. Episodic retrieval applies scope, optional entity, and \texttt{knownAt}; with no entity, it can return scope-relevant verified episodes. Semantic retrieval occurs only when an entity is supplied and applies scope, subject, optional predicate, \texttt{validAt}, and \texttt{knownAt}. Procedural retrieval applies scope and \texttt{knownAt}, but not \texttt{validAt}. Each repository applies the per-type limit. The result is a typed \texttt{MemoryRetrievalResult}; it does not flatten every record into one string.

\Needspace{0.68\textheight}

The service's central retrieval method makes the four read paths explicit:

\begin{minipage}{\linewidth}
\begin{lstlisting}[language=Java,caption={Cross-store retrieval applies scope and time filters without B1 scoring.},label={lst:ch20-memory-retrieval}]
public MemoryRetrievalResult retrieve(MemoryRetrievalQuery query) {
    var activeWorking = Optional.<dev.supplychain.agent.memory.working.WorkingMemorySnapshot>empty();
    if (query.workingMemoryId() != null) {
        var snapshot = working.findById(query.workingMemoryId()).orElseThrow(() ->
                new MemoryNotFoundException("Working memory not found: " + query.workingMemoryId().value()));
        if (!snapshot.scopeId().equals(query.scopeId())) {
            throw new SecurityException("working-memory scope does not match retrieval scope");
        }
        if (!snapshot.expiresAt().isAfter(query.knownAt())) {
            throw new MemoryNotFoundException("Working memory has expired at requested valid time");
        }
        activeWorking = Optional.of(snapshot);
    }
    var episodes = episodic.findVerified(
            new EpisodeQuery(query.scopeId(), query.entity(), query.knownAt(), query.limitPerType()));
    var facts = query.entity() == null ? java.util.List.<dev.supplychain.agent.memory.semantic.SemanticFact>of()
            : semantic.findActive(new SemanticFactQuery(query.scopeId(), query.entity(),
                    query.semanticPredicate(), query.validAt(), query.knownAt(), query.limitPerType()));
    var procedures = procedural.findActiveAt(query.scopeId(), query.knownAt(), query.limitPerType());
    return new MemoryRetrievalResult(activeWorking, episodes, facts, procedures);
}
\end{lstlisting}
\end{minipage}

This service deliberately performs deterministic, filter-based lookup. It does not assign activation, estimate retrieval latency, optimize downstream utility, or choose a context set under a resource budget. It also does not automatically copy returned items into working memory. A caller may use the typed result to construct a later reasoning request or feed a selection stage, but that handoff is not an automatic pipeline implemented by this service. Chapter 21 will examine B1's selection problem and B3's separate workspace competition/admission problem. Retrieval supplies candidate information; it is not a substitute for either one.

The historical query parameters also need careful interpretation. Episodic, semantic, and procedural repositories can decide whether a record was eligible at a requested \texttt{knownAt}. If a record has since been superseded or retired, the repository returns the currently stored immutable object, whose lifecycle status can still be \texttt{SUPERSEDED} or \texttt{RETIRED}; it does not materialize a separate historical version of the status. Semantic facts additionally apply valid-time filtering. Working memory is different: it is fetched by identifier and checked for scope and expiry, not reconstructed as a historical snapshot. These are useful time-aware filters, but they are not one uniform bitemporal query engine across all four memory types.

\section{Internal actions: retrieval, reasoning, and learning}
\label{sec:ch20-internal-actions}

Chapter 4 introduced retrieval, reasoning, and learning as internal actions. Retrieval brings information into a decision process; reasoning derives or assesses information; learning writes selected information to long-term memory. These operations can support one another, but the fact that one has occurred does not imply that the others have occurred.\CoALACite{Sections 4.2--4.4 and Figure 5}

The action module gives these operations typed handler contracts. Their descriptors identify them as internal actions and distinguish read-only work from memory writes. This makes the permission and effect boundary visible in the application instead of leaving every operation as an untyped function call.

\subsection{Retrieval action}

\texttt{MemoryRetrievalAction} is an internal, read-only handler. Its input is a \texttt{MemoryRetrievalQuery}; its output is a \texttt{MemoryRetrievalResult}. The action delegates to \texttt{MemoryRetrievalService} and declares a memory-retrieval capability. No working-memory update is hidden inside the call. This is the distinction between retrieving information and using it in the active context.

\subsection{Reasoning action}
\label{subsec:ch20-reasoning-action}

\texttt{ReasoningAction} receives a \texttt{ReasoningRequest} and delegates to an injected \texttt{Reasoning\allowbreak Provider}. The request identifies a task, a bounded context string, and a list of evidence references. The constructor for the request rejects a context longer than 48,000 characters and more than 200 evidence references, and it rejects duplicate evidence keys. These are application limits, not CoALA requirements.

\Needspace{0.75\textheight}

The result, \texttt{ReasoningAssessment}, is structured. It contains a summary, evidence-backed findings, hypotheses, assumptions, supporting evidence, information gaps, a confidence value, and a concise rationale. The fields are bounded in length and count. If a finding is labelled evidence-backed, the result must contain supporting evidence. The action also checks that the provider has not cited an evidence reference that was absent from the request:

\begin{minipage}{\linewidth}
\begin{lstlisting}[language=Java,caption={The reasoning action rejects citations outside the supplied evidence set.},label={lst:ch20-reasoning-action}]
ReasoningAssessment assessment = Objects.requireNonNull(
    provider instanceof ExecutionAwareReasoningProvider executionAware
        ? executionAware.assess(context, input)
        : provider.assess(input),
    "reasoning provider result");
Set<?> supplied = new HashSet<>(input.evidence());
if (!supplied.containsAll(assessment.supportingEvidence())) {
    throw new ActionExecutionException(new ActionFailure(
        ActionFailureCode.INVALID_INPUT,
        "Reasoning provider cited evidence that was not supplied in the request",
        false, false));
}
return assessment;
\end{lstlisting}
\end{minipage}

\subsection{Working-memory update and learning actions}
\label{subsec:ch20-learning-actions}

Reasoning does not automatically modify working memory. \texttt{WorkingMemory\allowbreak UpdateAction} is a separate memory-write handler. It checks that the requested scope matches the stored snapshot, that the expected version is current, and that the snapshot has not expired. It also supplies a request fingerprint for idempotency. Only after the preconditions pass does it call \texttt{WorkingMemoryService.put}.

Similarly, \texttt{EpisodeLearningAction} records an episode as unverified. Separate reviewer-facing operations handle episodic verification/rejection, semantic proposal/approval/rejection, and procedural validation/activation/rejection. The \texttt{LearningActionCatalog} exposes these operations through distinct, versioned action handlers and capabilities. The procedural handlers enforce author/validator/approver separation as described above; the episodic and semantic handlers do not enforce the same principal-identity comparison. Procedure predecessor retirement is not a separate catalog action: it occurs within the repository's replacement activation operation.

This is the implementation's meaning of explicit learning operations: the application can record an experience or propose a fact, but the write does not become trusted merely because a model generated it. The code does not fine-tune model parameters, modify its own Java source, or turn every outcome into a reusable procedure automatically. Those differences preserve the distinction in Chapter 4 between writing an experience, forming a semantic statement, and changing explicit procedural knowledge.

\section{External actions: perception and grounding in the modeled world}
\label{sec:ch20-external-actions}

CoALA's action space includes interaction with an environment. Chapter 5 distinguishes receiving an observation from carrying out a grounding action. In this application, those roles are represented by separate handler groups. The complete dispatch, capability, idempotency, and world-version gates were already introduced in Section~\ChapterNineteenActionBoundaryRef; this section focuses on what the agent receives and requests.\CoALACite{Section 4.2, ``Grounding actions,'' p. 10}

\Needspace{0.75\textheight}

\texttt{SupplyChainPerceptionActions} provides read-only operations for supplier, inventory lot, customer order, shipment, available inventory, and quality disposition. These handlers return an \texttt{Observation<T>} rather than a mutable domain object. \section{Planning: a candidate path over an isolated simulated state}
\label{sec:ch20-planning}

Chapter 6 introduced proposal as the part of the decision process that generates possible actions for consideration. Chapter 7 then distinguished evaluation from selection, and Chapter 8 placed these operations inside a repeated planning/execution cycle. Here, the central question is how the Java application represents a possible sequence of supply-chain operations before any of them changes the current simulated world.\CoALACite{Section 4.6, ``Planning'' and ``Proposal,'' pp. 12--13}

The starting contract is \texttt{PlanningRequest}. It binds the recovery objective to an initial supply-chain snapshot, the current working-memory snapshot, evidence references, available action definitions, hard constraints, a scoring profile, risk and authority policies, a planning-complexity classification, a resource/time budget, and a request timestamp. The class also carries additional governance inputs used by later mechanism services, including planner overrides, reusable recovery procedures, uncertainty directives, and alternative-hypothesis review. We will not unpack those B2, B4, and B6 additions here; their responsibilities belong to Chapters 22 and 23.

\Needspace{0.58\textheight}

A \texttt{PlanningState} represents one point in a candidate search. It stores the recovery-objective identifier, the root-world version, the branch's current snapshot, the ordered path of proposed actions, and accumulated evidence. Its constructor enforces a useful invariant: the branch snapshot version must equal the root version plus the number of actions in the path. It also prevents the same planning-action identifier from appearing twice in one path. Advancing a state creates a new object and adds the action's supporting evidence:

\begin{minipage}{\linewidth}
\begin{lstlisting}[language=Java,caption={A planning transition creates a new path state rather than mutating the root.},label={lst:ch20-planning-state}]
public PlanningState advance(SupplyChainSnapshot nextWorld,
                             PlanningAction action) {
    var actions = new ArrayList<>(actionPath);
    actions.add(Objects.requireNonNull(action, "action"));
    var refs = new LinkedHashSet<>(evidence);
    refs.addAll(action.supportingEvidence());
    return new PlanningState(objectiveId, rootWorldVersion,
        nextWorld, actions, List.copyOf(refs));
}
\end{lstlisting}
\end{minipage}

A \texttt{PlanningAction} binds several things that must remain consistent: a planning-action identifier, an action descriptor, a domain recovery action, a simulator command, an impact estimate, supporting evidence, and assumptions. The identifier is also used by the command. This prevents the candidate description and the command that is simulated from referring to unrelated operations.

The \texttt{PlanningWorldModel} defines three operations: create an initial state, list actions available from a state, and apply a proposed action to produce a new state or a typed rejection. Its contract requires deterministic behavior and no external side effects. The \texttt{PlanningRequest} also validates that every supplied action definition is a grounding action with a domain-write effect and that its required capability falls within the trusted proposal scope. \texttt{SimulatorBackedPlanningWorldModel} implements that contract using the same deterministic supply-chain simulator introduced in Chapter 19. Before applying a transition, it checks that the action descriptor is included in the request, that the capability is inside the trusted proposal scope, and that the typed recovery action matches the simulator command.

The actual transition is deliberately small:

\begin{minipage}{\linewidth}
\begin{lstlisting}[language=Java,caption={The planning world model applies a command to a branch state only.},label={lst:ch20-simulator-world-model}]
public WorldTransition apply(PlanningRequest request,
                             PlanningState state,
                             PlanningAction action) {
    requireState(request, state);
    Objects.requireNonNull(action, "action");
    validateAllowedAction(request,
        request.actionDefinitionsById(), action);
    try {
        var result = simulator.simulate(
            state.world(), action.simulationCommand());
        PlanningState next = state.advance(result.snapshot(), action);
        return new WorldTransition.Applied(next);
    } catch (DomainViolation | IllegalArgumentException ex) {
        return new WorldTransition.Rejected("DOMAIN_TRANSITION_REJECTED",
            ex.getMessage() == null
                ? "domain rejected the transition" : ex.getMessage());
    }
}

The simulator receives the branch snapshot from \texttt{PlanningState}, not the current snapshot held by \texttt{SupplyChainSimulationWorld}. The result is placed into a new planning state. The method does not call the world adapter or commit a change to the current modeled environment. Notice the placement of the \texttt{try} block: \texttt{requireState}, the null check, and \texttt{validateAllowedAction} run before it, so invalid request ownership, missing action definitions, scope violations, and action/command mismatches fail fast rather than becoming typed transition rejections. This makes it possible for a planner to explore an infeasible domain branch without corrupting the state on which the real decision is based, while keeping request and authority validation distinct from domain-transition rejection.

There are therefore two distinct uses of the simulator logic. During planning, it computes what the world would look like if a candidate path were followed, but only inside an isolated branch. During grounding, an authorized action is sent through the dispatcher and world adapter to change the current modeled environment. The internal rollout is a structured, deterministic simulator application to a branch; it is not a language model imagining a consequence and it is not environmental feedback. This is the implementation counterpart of the distinction already developed in Chapters 6--8 between using a structured simulator to develop/evaluate a proposal, reasoning about possible consequences, and receiving an observation after an external interaction.\CoALACite{Section 4.6, ``Evaluation,'' p. 12; ``Execution,'' p. 13}

The sequential planner builds one candidate path by asking its provider for the next action at each step. The provider is responsible for choosing from the currently available actions. The planner checks that the returned evidence references are among those supplied by the request, working memory, or current planning state. It then applies the selected action to the planning branch and evaluates the resulting state. The implementation cannot resume a persisted search session; it rejects a request that supplies a resume-session identifier.

The bounded alternative search expands structured partial recovery plans. It ranks the available domain actions and expands only within configured branching, depth, and resource limits. The default \texttt{DeterministicThoughtActionRanker} orders reusable recovery actions first and then uses a transparent estimate based on service progress, cost, time, risk, and robustness. The code comment makes clear that this is not an LLM thought generator. “ToT-inspired” is a descriptive label for the bounded branching approach, not a claim that the implementation reproduces a separate research system.

The MCTS planner uses a different search organization. It expands a tree, selects nodes through an upper-confidence-bound rule, evaluates simulator-backed rollouts, and propagates rewards through visited nodes. Its randomization is seeded so that the test can verify repeatability under the same inputs and configuration. The class describes the approach as a RAP-inspired, domain-grounded MCTS adaptation and explicitly rejects the claim that it is a faithful RAP reproduction. That qualification should remain visible whenever the strategy is named.

\section{Evaluation and selection: a high score is not permission}
\label{sec:ch20-evaluation-selection}

Part I separated evaluation from selection. Evaluation assigns values or checks properties of candidate actions. Selection determines what happens to the candidate set. Neither operation should be confused with execution authorization.\CoALACite{Section 4.6, ``Evaluation'' and ``Selection,'' pp. 12--13}

The application separates the evaluator contract from its deterministic implementation. The main types are \texttt{CandidateEvaluator}, \texttt{DeterministicCandidate\allowbreak Evaluator}, \texttt{PlanEvaluation}, and \texttt{PlanCandidate}. A candidate is not accepted merely because a planner returned it. The deterministic evaluator reconstructs the proposed action path from the request's trusted initial planning state. At each step, it checks that the proposed action remains available and exactly matches the canonical action definition, then applies it through the world model. After replay, it compares the resulting snapshot with the snapshot claimed by the proposed state. It also checks objective identity, root-world version, hard constraints, deadline, risk threshold, and the structural validity of the action-impact estimates.

If replay and hard constraints pass, the evaluator calculates a transparent weighted score. The implemented factors are expected fulfillment progress, normalized estimated cost, timeliness, aggregate risk, and robustness. The impact values are carried by the canonical planning-action definitions and are aggregated by the evaluator; replay checks the world transition and candidate-state consistency, but does not derive those estimates from the simulator's before/after state or establish that they are calibrated to observed outcomes. This is an engineering scoring policy, not a formula prescribed by CoALA or a universally optimal objective function.

One implementation assumption deserves special attention. The aggregate risk calculation multiplies per-action survival estimates, which treats action risks as independent for the purpose of that estimate. The code documents this as an explicit engineering assumption. Real action risks may be correlated; the current score should therefore be read as the output of the configured model, not as a calibrated probability that the plan will succeed.

The evaluator also exposes a limitation rather than hiding it. If a request includes \path{PRESERVE_PROTECTED_CUSTOMER_COMMITMENTS}, the current domain model cannot identify the protected commitments needed to verify the constraint. The evaluator fails closed and records a violation. It does not claim that the constraint has been checked successfully. This is an important example of how a hard constraint should behave when the application lacks the data needed to verify it.

Feasibility and approval are separate. \texttt{PlanEvaluation.approvalRequired} records whether a downstream governance requirement applies to the proposed write. It is not itself a hard planning violation. A candidate can be feasible and still require approval before it may proceed. The \texttt{PlanCandidate} type describes itself as an auditable proposal; it is not approved and cannot be executed directly.

Four decisions must therefore remain distinct:

\begin{enumerate}
  \item \textbf{Planner-method routing} chooses which registered strategy will search. This is the responsibility of \texttt{PlannerRouter}; B4's authority over persistent method choices is explained in Chapter 23.
  \item \textbf{Candidate evaluation} replays a proposed path, checks feasibility constraints, and assigns evaluation values. \texttt{CandidateEvaluator} does not choose a candidate.
  \item \textbf{Strategy-specific ordering and retention} happen inside the planner implementation. The sequential strategy extends the single path chosen by its injected provider; bounded search ranks successors, prunes branches, and sorts the retained candidate list; MCTS selects tree nodes during search and orders the extracted candidate list by evaluation score. There is no shared \texttt{CandidateSelector} service in the inspected planning module, nor a generic CoALA-style reject-and-return-to-proposal loop implemented as a separate component.
  \item \textbf{Execution authorization} decides whether a particular state-changing action may be dispatched. Chapter 19 introduced the action gates; Chapter 24 will show their place in the full workflow.
\end{enumerate}

\BookDiagram[0.50\textheight]
  {Tex/diagrams/generated/part3/chapter20/evaluation-selection-authority.png}
  {PlannerRouter selects a strategy; CandidateEvaluator evaluates a path but does not select it; each strategy implements its own search-time ordering and candidate retention. The focused evaluator tests make these boundaries concrete. One accepts a simulator-replayed plan and confirms that approval is reported as a governance requirement. Another rejects a proposed state that does not match replay. A third rejects a plan that exceeds the configured hard-risk threshold. A fourth verifies fail-closed behavior when the protected-customer-commitment constraint cannot be checked by the current domain model. These assertions demonstrate the implemented checks; they do not establish that every possible business constraint is represented or that the score is empirically calibrated.

\section{A bounded code trace: from memory result to plan candidate}
\label{sec:ch20-bounded-trace}

We can now connect the contracts in one short trace. The purpose is to make the handoffs visible, not to imply that one test runs every operation in this exact order. The trace is a pedagogical composition of component behavior supported by focused tests; the full runtime composition is reserved for Chapter 24.

\begin{enumerate}
  \item \textbf{Open or load active context.} The application obtains a working-memory snapshot bound to the relevant memory scope. The snapshot has a version and expiry time; updates will later require the expected version.
  \item \textbf{Retrieve typed memory.} A \texttt{MemoryRetrievalQuery} supplies the scope, relevant entity, temporal parameters, and per-type limit. The result carries an optional working-memory snapshot and separate collections of verified episodes, active semantic facts, and active procedures.
  \item \textbf{Assess supplied evidence.} The caller constructs a \texttt{ReasoningRequest} from an explicit task, bounded context, and evidence references. \texttt{ReasoningAction} returns a structured assessment and rejects citations that were not supplied.
  \item \textbf{Construct a bounded planning request.} The request binds the recovery objective and initial snapshot to the working-memory version, evidence, permitted action definitions, constraints, score/risk/authority policies, and planning budget.
  \item \textbf{Explore one candidate branch.} The planning world model creates a root \texttt{PlanningState}, lists trusted available actions, and applies a selected candidate through the deterministic simulator. The result is a new branch state; the current world adapter is unchanged.
  \item \textbf{Replay and evaluate.} The evaluator replays the path from the request's initial state, verifies action availability and snapshot equivalence, checks hard constraints, and produces a \texttt{PlanEvaluation}. The candidate factory returns an auditable \texttt{PlanCandidate} if the result is feasible.
  \item \textbf{Stop before execution.} The trace ends with a proposal. It does not obtain application-level approval, dispatch a grounding action, or change the current simulated world. Those steps belong to the execution path explained in Chapters 19 and 24.
\end{enumerate}

\section{Chapter recap}
\label{sec:ch20-recap}

\begin{chapterrecap}
\hyphenpenalty=10000
\exhyphenpenalty=10000
CoALA's three dimensions provide a practical map for reading the application: memory services represent information storage; typed handlers expose internal and external actions; and planning plus the later runtime coordinates decisions over time. The mapping is many-to-many rather than one box per class or Maven module.

The four memory responsibilities remain distinct. Working memory is active, scope-bound, versioned context. Episodic memory records experience but requires separate review before trusted retrieval. Semantic memory manages facts with provenance, admission status, and valid-time/known-time filters. Procedural memory manages versioned procedure records through explicit lifecycle transitions; replacement activation retires the predecessor within the repository operation, and the store is not a GraSP skill-DAG executor. Cross-store retrieval returns typed results using different per-store filters; it does not perform B1 scoring or B3 workspace admission, and historical eligibility does not mean that the currently stored object is materialized in its old lifecycle state.

Internal actions are also separate and caller-composed. Retrieval reads memory; reasoning returns a bounded, evidence-referenced assessment; working-memory updates and episode recording are separate writes. Episodic and semantic review use separate capabilities and evidence, while explicit author/validator/approver identity separation is enforced in the procedural lifecycle. External perception returns provenance-bearing observations, while grounding requests state changes in the simulator. During planning, the deterministic simulator applies candidate commands to isolated branch states. It does not commit those branches to the current simulated world.

The sequential, bounded-search, and MCTS planners share one contract but explore in different ways. Candidate evaluation replays paths and checks configured constraints, while each strategy manages its own search ordering and candidate retention; there is no common candidate-selection service. A feasible or highly ranked candidate remains only a proposal and still requires downstream authorization before grounding.
\end{chapterrecap}
