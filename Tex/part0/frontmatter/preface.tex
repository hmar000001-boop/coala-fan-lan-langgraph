\chapter*{Preface}
\addcontentsline{toc}{chapter}{Preface}

Language agents are often introduced through visible capabilities: they can retrieve information, reason over a request, call tools, and produce an answer. Those capabilities are important, but they do not by themselves explain how an agent organizes its state, decides which internal operation should happen next, preserves an objective across interruptions, or determines whether an external action is safe and authorized. To understand a complex agent, we need to examine both its cognitive organization and the mechanisms that control its behavior.

This book brings together two research perspectives that address different levels of that problem. Part I develops the \emph{Cognitive Architectures for Language Agents} (CoALA) framework on its own terms. CoALA provides an architectural vocabulary for memory, internal and external actions, and decision-making. Part II examines Fan and Lan's mechanism-level review, which asks what concrete state, control, triggering, persistence, failure, learning, and resource responsibilities sit behind broad capability labels. The two contributions are related, but they are not interchangeable: the mechanism analysis in Part II is not retroactively attributed to the original CoALA framework. The book treats each source according to its own scope and evidence.\cite{sumers2024coala,fanlan2026mechanisms}

Part III turns from analysis to engineering. It follows one request-driven supply-chain disruption-management application implemented in Java and exercised against a deterministic simulated world. The application provides a concrete setting in which to examine typed domain rules, memory services, internal and external actions, planning strategies, selected mechanism responsibilities, graph orchestration, persistence, approval, execution, and reconciliation. It is deliberately one connected application rather than a collection of unrelated demonstrations.

The engineering work is selective and explicit about its boundaries. The application provides engineering counterparts for selected responsibilities associated with B1, B2, B3, B4, and B6; it does not claim to reproduce every source mechanism in full, and it does not present B5 or GraSP as implemented. CoT-style sequential planning, bounded ToT-inspired search, and domain-grounded RAP-inspired Monte Carlo tree search are implemented as separate planning strategies. LangGraph4j coordinates the application workflow, while LangChain4j provides a model-facing adapter boundary. These frameworks do not themselves implement the planning algorithms or the cognitive mechanisms. The Java domain and application services remain responsible for business invariants, feasibility, and authority.

The word \emph{production} in the title signals the engineering concerns taken seriously throughout the book: explicit contracts, typed state, domain invariants, bounded resources, authority checks, persistence, recovery, testing, and traceability. It should not be read as a claim that the reference application is a deployed production service. The application is a teaching and engineering reference. Its external supply-chain world is simulated; it is not connected to a live ERP, warehouse, supplier, carrier, or order-management system. The implementation demonstrates selected design decisions and tested behaviors, not universal production readiness.

A similar distinction applies to evidence. Statements about CoALA and Fan and Lan are grounded in the cited research. Illustrative scenarios are book-created teaching examples. Architectural mappings, interfaces, and runtime choices in Part III are engineering decisions made for this application. Tests establish only the behaviors asserted by their fixtures and checks; they do not, by themselves, establish empirical superiority, general performance, or correctness in every external environment. Where the source papers leave a mechanism underspecified, or where the application implements only part of a responsibility, that boundary is stated rather than filled with an invented claim.

The intended reader has basic programming knowledge and an interest in language agents, cognitive architectures, or complex software systems. No prior familiarity with CoALA or Fan and Lan's review is required: the first two parts build the relevant concepts before the implementation is introduced. Readers who want to run or modify the Java application will also benefit from familiarity with Java and Maven; the conceptual arguments can still be followed without setting up the code.

The aim is not to argue that one architecture or framework is sufficient for every agentic system. It is to give readers a disciplined way to move between architectural ideas, mechanism-level explanations, implementation choices, and the evidence that supports them. The result should be useful both to readers studying how language agents are organized and to engineers asking how those ideas can be made explicit in a real codebase.
